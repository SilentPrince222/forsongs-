# 🏗️ Архитектура проекта Forsong
Версия: 1.0 | Последнее обновление: 28.04.2026

> ✅ Этот документ является главным контрактом для всего проекта. Любые изменения в коде должны соответствовать правилам описанным здесь.
> ✅ Архитектура разработана специально для долгой поддержки, масштабирования и полного рефакторинга отдельных частей без слома всего приложения.

---

## 🎯 Основные принципы
1. **Нет регрессий** - можно переписать любую часть проекта и ничего не сломается
2. **Нулевая связанность** - компоненты не знают о существовании друг друга
3. **Заменяемость** - любая реализация может быть заменена за 1 час
4. **Тестируемость** - все части тестируются независимо
5. **Отменяемость** - любая операция может быть отменена в любой момент
6. **Никаких магии** - все явно, все очевидно

---

## 📚 Слоистая архитектура (Чистая архитектура)

```
┌──────────────────────────────────────────┐
│          PRESENTATION (GUI)              │  ← Только отображение
├──────────────────────────────────────────┤
│          APPLICATION (Сервисы)           │  ← Бизнес логика
├──────────────────────────────────────────┤
│        INFRASTRUCTURE (Реализации)       │  ← Работа с внешним миром
├──────────────────────────────────────────┤
│              DOMAIN (Ядро)               │  ← Ни от кого не зависит
└──────────────────────────────────────────┘

✅ Зависимости идут ТОЛЬКО ВНИЗ. Никогда наоборот.
✅ Верхний слой может знать о нижнем. Нижний НИКОГДА не знает о верхнем.
```

## 📜 Правила которые НИКОГДА НЕ НАРУШАТЬ

### ❌ ЗАПРЕЩЕНО:
1. Импортировать что то из `gui`, `infrastructure`, `application` в доменный слой
2. Прямые вызовы между компонентами. Только через события.
3. Хардкодить зависимости. Все через DI контейнер.
4. Блокирующие вызовы в главном потоке GUI
5. Глобальные переменные и состояния кроме EventBus
6. Писать бизнес логику в GUI компонентах
7. Делать больше одной ответственности в классе/функции

### ✅ РАЗРЕШЕНО:
1. Импортировать из доменного слоя в любой другой
2. Подписываться на события любого компонента
3. Заменять реализацию любого интерфейса не трогая остальной код
4. Добавлять новые события и новые сервисы
5. Полностью переписать любой слой не меняя остальные

## 🔌 Система взаимодействия компонентов

### ✅ Правильный способ:
```
✅ SearchService публикует событие TrackFoundEvent
✅ DownloadService подписывается на TrackFoundEvent
✅ GUI тоже подписывается на TrackFoundEvent
✅ Никто никого не вызывает напрямую
✅ Можно добавить ещё 10 подписчиков и ни кто не узнает
✅ Можно отключить любой подписчик в любой момент
```

### ❌ Неправильный способ:
```
❌ SearchService вызывает DownloadService.download()
❌ SearchService вызывает GUI.update()
❌ Теперь все связаны на всегда. Нельзя протестировать отдельно.
```

## 🔄 Жизненный цикл операции

1. Пользователь нажимает кнопку "Поиск"
2. GUI отправляет команду `SearchCommand` в EventBus
3. SearchService подписан на эту команду и начинает поиск
4. По мере получения результатов SearchService публикует `TrackFoundEvent`
5. GUI подписан на это событие и отрисовывает новые треки
6. Если пользователь закрыл вкладку - GUI просто отписывается от событий
7. SearchService продолжает работать, он даже не знает что GUI больше нет

## 📐 Правила для масштабирования в будущем

| Когда будем добавлять | Что нужно сделать |
|------------------------|-------------------|
| Новый источник музыки | Реализуй интерфейс `BaseParser` и зарегистрируй в DI. ВСЕ. Больше ничего менять не нужно. |
| Новая функция | Добавь новый сервис в `application/services`. Подпишись на нужные события. |
| Новый виджет | Создай виджет, подпишись на события. Никаких других изменений. |
| Замена GUI на Qt/WEB | Просто напиши новый слой presentation. Весь остальной код остаётся как есть. |
| Замена SQLite на PostgreSQL | Перепиши репозитории. Все остальные 95% кода ничего не заметят. |
